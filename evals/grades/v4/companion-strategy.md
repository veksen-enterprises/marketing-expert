## Errors

1. **Diagnosis rests on a misread count (unlabelled inference):** "You already have supply: the production database holds 3,932 distinct screenshots (packages/cli/corpus/README.md line 11) ... So the real unknown is whether the watch loop works". The count is cumulative and covers every quality. It includes history-walk backfill, and the API skips watch matching for backfill ("Listings and captures it creates are marked `backfill`, so the API skips watch matching, the public new-item announce...", bot README:93-95). A watch fires on new items in its segment per week. That rate is what the answer's own open question 3 asks for ("How many items list per week"). The repo's only segment measurement points the other way. ADR 0006:10-14 (read in full; `scan_source` listed line 10) gives "25 of them, 18% of the rare and crafted table" and "a production table of 141 items" for rares, measured 2026-08-04. The answer also contradicts itself: Move 2 stops if "supply per watch is too thin". Round 3 labelled its diagnosis "(labelled guess)". This one has no label.
2. **Avatar overstatement (repeat of round 3 Error 3, softened):** "The public item page shows 'Owned by <Discord name>' with the avatar (apps/app/src/routes/items.$id.tsx 249–300)". `OwnerAvatar` renders the Discord image only `if (owner.avatar)` (line 258). Otherwise it shows an initial (lines 267-273). The bot sends no avatar for a poster: `ListingAuthor` (listing-client.ts:4-8) has `discordId`, `username` and `displayName` only, and avatars are written at sign-in (`routes/auth.ts:138,149`). "on every public item page" is gone. "with the avatar" is still wrong for posters who never signed in, who are most owners. The privacy finding stands, because the name is public.
3. **Feed reach overstated (residue of round 3 Error 6):** "The public feed and item links carry your name into channels (your built-in sharing loop)." The feed posts to the one channel named by the single global `DISCORD_PUBLIC_WEBHOOK_URL` (config.ts:34). The answer says itself that it is "active only when its webhook is set" and does not know whether it is set. It is not in any trade channel, and the bot posts nothing in trade channels (the answer's own finding: "the only Discord write I found is the watch DM"). Only links that traders paste themselves travel. The plural "channels" and "built-in loop" describe a loop that does not run today.
4. **The removal route is labelled in a way that hides what it does (omission):** "no API route that lets a poster remove an item or screenshot (the only deletes in apps/api/src/routes are sessions, stash links and watches)". The `user-items.ts:280` delete is described in code as "Remove ownership of an item". It deletes the `user_items` row, which is the row the public "Owned by" line is read from (items.ts:297-308 `.from(userItems)`). So a signed-in owner can already remove their name through the API, but not from the UI ("Ownership actions are deferred — wiring to /me/items is follow-up", items.$id.tsx:200). "Stash links" matches the UI's "Add to Stash" button, so the label is not invented. But in a paragraph about removal paths, the reader is never told that half of one exists. The headline claim (no route removes the item or screenshot) is accurate.
5. **Metrics measure a state the data does not have:** Move 2: "Metric: share of the 20 with a live watch after 30 days". Move 3: "Stop: new watches don't survive 30 days." `item_watches` (schema.ts:464-481) has `id`, `userId`, `params` and `createdAt`, with no active flag, expiry or last-seen time. A watch "survives" unless its owner deletes it, so a trader who stopped caring still counts as retained. The other Move 2 metric ("alerts per watch per week") is measurable, but it measures supply, not whether traders come back. Neither move names a trader action, such as a contact with an owner, that the database can count. The answer's "log each alert and each contact with an owner" is a manual log, which is fine for 20 traders but is not stated as the retention metric.
6. **Publisher rule applied beyond its scope (repeat of round 3 Error 5, softened):** "No payments, paid tiers or price fields. Blizzard's API terms restrict paid versions and Blizzard bans real-money trading [first-party, read via search snippets]." The section header's "these are examples, not legal advice" is dropped. "forbid" became "restrict", and A1 now says "Blizzard's terms" generally, which is better.
