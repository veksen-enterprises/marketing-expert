## Errors

1. **Wrong line reference (misattribution):** "Your README (lines 18-19) says the message-content intent needs Discord's approval at 100 servers." `apps/bot/README.md` lines 18-19 are the channel-permissions list ("- `View Channel`", "- `Read Message History`..."). The 100-server sentence is at lines 14-15: "It's free and takes effect immediately under 100 servers; at 100+ it needs Discord's approval." The substance is correct and the location is wrong. INSTRUCTIONS #0 asks for "the file (and line) you actually opened".
2. **Altered quote:** "The API describes the item route as 'public, with its owner' (`apps/api/src/routes/items.ts:254`)." The text at line 254 is "Fetch a single persisted item by id (public), with its owner, when it was posted to trade...". The quote marks join two separate fragments. The meaning survives, but the quoted words are not in the file.
3. **Overstatement of code behaviour:** "shows 'Owned by <Discord name>' with the Discord avatar on every public item page." `OwnerAvatar` (items.$id.tsx:250-274) renders the Discord CDN image only `if (owner.avatar)`, and otherwise shows an initial letter. The bot passes no avatar for a poster: `ListingAuthor` in `apps/bot/src/listing-client.ts:4-8` has only `discordId`, `username` and `displayName`. Avatars are written at Discord sign-in (`routes/auth.ts:138,149`). Items with no owner show "No owner yet" (line 303). The name is public, so the privacy finding stands. For posters who never signed in, which is most of them, there is no avatar, and "every public item page" is not accurate.
4. **Move 2's cheapest test misdescribes the code (a build presented as a switch):** "In that partner server, turn on the public new-item feed, with links to 'watch similar items'... set the webhook for one server. Tag the feed's links, for example `https://companion.example/search?utm_source=...&utm_content=new-item-embed`." The issues:
   - The embed's only link is fixed in code: `const url = \`${appUrl}/items/${itemId}\`` (`discord-public-log.ts:88`). It goes to the item page, not `/search`, and it carries no UTM tags.
   - `DISCORD_PUBLIC_WEBHOOK_URL` is one global value (`config.ts:34`). There is no per-server feed, so "set the webhook for one server" sends every item from every channel the bot reads into the partner's channel.
   - The item page already has a "Find Similar Rolls" link (items.$id.tsx:204-212) that leads to the search page and its watch button. The path the answer wants exists, but through the item page, which the answer does not mention.

   The move as written needs a code change to the embed builder, presented as configuration. A founder following the "cheapest test" would find it isn't one.
5. **Publisher rule applied beyond its scope, with a hedge dropped:** "Blizzard's API terms forbid paid versions" (A1) and "Blizzard's API terms forbid paid versions and charging players [first-party, via snippets]" ("What not to do yet"). These are Blizzard's *Developer API* Terms, which govern apps that call Blizzard's APIs. GameX Companion calls none: it OCRs Discord screenshots, and I found no Blizzard API use in the repo (the only `battle.net` hits are links to Arreat Summit reference pages). The playbook heads that section "rules differ; these are examples, not legal advice" (line 58). Round 2 hedged it ("its examples are from other titles, so this is not verified for GameX"). This round states it flatly twice and lets it drive the business-path advice. The likely conclusion (stay free, no RMT) is reasonable, but the stated reason is wrong for this product.
6. **Unsupported claim in the opening answer:** "Your second is the bot's own output (the new-item feed and the DMs), which already sits where traders are." Later the answer says it "can't tell if it's switched on in production". The feed posts to whatever channel the single webhook names, a GameX Companion-controlled channel, not the trade channels. Move 2 exists precisely to move it into a partner server. So the opening claim contradicts the answer's own caveat.
7. **Season timing still not worked out from the repo (partial repeat of round 2's Error 6):** "A4. Season 14 is running now. The next ladder reset falls in the next few months. I haven't checked the date." The tool log shows it opened `knowledge/warlock-expansion.md` (first 30 lines). Line 3 reads "released Feb 20-21, 2026 alongside Ladder Season 13". It also grepped the PlannerSite notes ("observed on 2026-09-21... (Season 14)"). Those two points bound when Season 14 started and give a rough estimate for the next reset. The answer neither makes that estimate nor considers that Season 14 may still be in its busy early weeks now (2026-10-04), which matters for Move 3's timing.
8. **Data-handling check incomplete (lost from round 2):** the answer tells the founder that "Moderators will ask what the bot stores and shows". It covers only the owner name. It drops round 2's catch that every screenshot is kept as a "training capture" (`capture-client.ts:81` "Posts a training capture (screenshot + OCR result)"; `ingest-handler.ts:33`). That capture is exactly what the playbook's data rules make a moderator question: "bans training AI models on message content without..." (community-and-hobby-products.md line 34; also line 56 "no AI training on message content"). INSTRUCTIONS #0 asks to check "data-handling... (what is sent, stored, kept local...)" line by line.
9. **Move structure:** Move 3 has no time box, and its cheapest test is two actions (a pinned post *and* streamer outreach). INSTRUCTIONS #6: "each is one action, not a bundle. For each: ... a time box". "Build item lifecycle soon" is a "do" listed under "What not to do yet".
10. **Instruction breach: length.** 1,323 words in the answer section (`wc -w`) against "keep the whole answer under about 1,200 words", about 123 words (~10%) over. The two pre-move sections are what tips it over: "What the repo says is shipped" (~117 words) and "Fix these before you approach moderators" (~192 words). INSTRUCTIONS #9 says to cut inventories first.
11. **Tool use: go/no-go numbers unmodelled (repeat).** No calculator, so every stop condition is qualitative. The answer says it estimated nothing, which is honest. It never says that the `marketing_strategy` economics step does not apply to a free product, beyond A1's one line.
