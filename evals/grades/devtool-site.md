2. **It missed that "How it works" is out of date, and fix #3 is built on that stale page.** index.astro:241–281 sells "No agents to install on prod… `docker run`… Paste a connection string… Read-only role". docs/guides/getting-started.md says: "The instance stores the string… There is no `docker run` command and nothing to install on your side." ADR 0026 (built 2026-08-24) records that the old "this never leaves your container" copy was untrue. The proposed disclosure line goes under a step that no longer exists, and it leaves out the most sensitive fact: DBTool now **stores the connection credential**. The suggested wording "We never read rows" is also stronger than the FAQ, which says "we never see your full rows", while the most-common values are sampled from rows.
3. **It missed a contradiction on the pricing page itself.** pricing.astro:263 says "We see each query's shape and run a generic plan. Parameter values aren't included.", while pricing.astro:365 says the statistics "include sample values from your columns". (devtool-strategy missed this too.)

6. **A sample-size claim made from memory** ("thousands of visitors per version"). See item 5.
7. **Tool output error (server bug, handled correctly).** `check_ai_crawler_access` returned `"No robots.txt found: every bot is allowed by default."` and `llmsTxtFound: false`. I reproduced it. The sandbox proxy answers `/robots.txt` with **HTTP 403, text/plain, `x-deny-reason: host_not_allowed`**. The tool treats any non-OK, non-5xx response as "no robots.txt", so a block is reported as "everything allowed". The earlier fix (351fa5b, "never report 'allowed' for a site we couldn't check") covers only fetch exceptions, not 4xx responses. The assistant correctly discounted the result.

## Server attribution (ranked, most impactful first)

### Tool gave wrong or misleading data

1. **`check_ai_crawler_access` reports a blocked fetch as "every bot allowed".** *File:* src/lib/aiCrawlers.ts `checkAiCrawlerAccess`. *What:* (a) Return `robotsStatus` and `robotsContentType`. (b) Treat 401/403/407/429 as **not checked**, not as "no robots.txt", and treat a response with an `x-deny-reason`/proxy signature or a text/plain body under ~200 bytes the same way. Return `checked:false` and the same "Nothing was checked" message used for exceptions. (c) Report only a real 404/410 as "No robots.txt: allowed by default". (d) Flag a 200 `text/html` response on /robots.txt and /llms.txt as its own finding ("returns an HTML page with status 200, probably a catch-all fallback; crawlers see no rules and soft 404s"). (e) Return `llmsTxtFound: null`, not `false`, when the llms.txt fetch is blocked. *Why:* this is the second eval where the tool told the advisor "allowed by default" for a site it never reached. The earlier fix only handled thrown errors. Item (d) would also have turned the advisor's guess ("very likely returns the home page") into a measured finding on a reachable site.

### Server instructions, prompts or playbooks that caused the weakness

2. **The teardown prompt never checks the page against the product.** *Files:* src/prompts.ts `landing_page_teardown`, and INSTRUCTIONS rule 0 in src/server.ts. *What:* Add a step before the critique: "Product truth check. List the page's factual claims: features and their 'soon'/'roadmap' labels, setup steps, prices, data handling, how it works. Check each against the product's own docs, changelog, release notes or repo (docs/, ADRs, packages). A site that describes an older product is often the first fix, ahead of copy." Add to rule 0: "If a fact can be checked in files or pages you can reach, check it. Don't list it as an assumption." Also give the prompt optional `sourcePath` and `docsUrl` arguments, so a run that can't fetch the site gets told to read the source and docs. *Why:* this is the main cause of the score loss. The same server got this diagnosis right in devtool-strategy only because that run happened to open apps/docs. This prompt is URL-only and steers attention to the page alone. That is why the stale MCP/alerts/`docker run` content was turned into questions, and why fix #3 was written for a setup flow that no longer exists. (The assistant shares the blame: cases.md lists docs/adr.)
3. **The AI-visibility guidance ignores coding agents and dev-tool discovery.** *Files:* knowledge/ai-assistant-visibility.md, and the hard-coded llms.txt finding in src/lib/aiCrawlers.ts (lines 137–141). *What:* Add a section for developer tools. Coding agents (Claude Code, Cursor, Codex) both recommend tools and read docs while they work. Cover agent-readable docs (markdown docs, skill files, `llms.txt` for **docs** sites, labelled practitioner and not proven), MCP registries, the GitHub README and package registries as places to be found, and test questions run in coding agents as well as in ChatGPT/Perplexity. Change the tool's finding from a blanket "Not a problem" to "No evidence web assistants use it; dev-tool docs often serve one for coding agents". Also write the `developer-tools` playbook proposed in the devtool-strategy grade (still missing from knowledge/). *Why:* the advisor repeated the tool and playbook line "no evidence that assistants use it" for a product whose VISION makes agents first-class readers and whose docs already publish `/skill.md`. That is the item-4 gap.
4. **There is no site-review prompt, so the answer sprawled.** *File:* src/prompts.ts, a new `site_review` prompt (or an extension of `landing_page_teardown`). *What:* Combine (i) the product truth check, (ii) a cross-page consistency pass (price, product name, method wording; `crawl_site` could pull `$` amounts and the h1/title per page and flag differences), (iii) technical checks (status codes for unknown URLs, robots.txt, sitemap, og:image on every layout), and (iv) AI visibility. Cap the output: "top 3 fixes, then at most 3 one-line cleanups; drop the rest." *Why:* the user asked a combined SEO and AI question. The advisor stitched together a teardown prompt and a diagnosis prompt and returned about 15 actions, against INSTRUCTIONS rule 5. A cross-page check in a tool would also have caught pricing.astro:263 vs :365.
5. **No pricing guidance on lifetime deals.** *File:* knowledge/pricing.md. *What:* Add a short section on lifetime deals: how many months of subscription revenue they equal, the risk of promising "everything, forever" for features not built yet, capping and retiring the offer, and labelling the evidence as practitioner. *Why:* the $100 lifetime offer that includes future MCP and rewrites sits on both pricing surfaces, and neither this run nor devtool-strategy treated it as a decision.
