## Errors

1. **Factual (code misread, presented as a code check):** "**Open:** item lifecycle (VISION open question 1). A sold item keeps firing watch DMs. That is the biggest threat to keeping watchers." In the code a watch fires once per item, only when the item is created. `matchWatchesForItem` in `apps/api/src/services/watch-matcher.ts` is "Matches a newly-created item against every active watch", and the `(watch_id, item_id)` unique key makes a repeat "a no-op". A sold item never fires again. The sentence paraphrases VISION's "A sold item shouldn't keep firing notifications", but it sits under "I checked the code, not just the docs". The real lifecycle harms are different: stale items in search results, and reposts. ADR 0006 says "The same physical item posted twice is already two permanent rows — 25 of them, 18%". Every repost is a new item, so watchers get a second DM for an item they already saw. The proposed fix ("expiring them after N days unless reposted") addresses staleness in search. It does nothing about duplicate DMs, which need ADR 0006's identity work. So the answer gets wrong what most threatens watcher retention.
2. **Missed existing asset (repeat of round 1):** the API posts every newly listed item to a public Discord channel through a webhook, with an embed, tooltip image and watcher count (`apps/api/src/services/discord-public-log.ts`: "Announces one newly-created item to the public Discord channel"; also `announce-item.ts`, `publish-new-item.ts`). The bot README even mentions "the public new-item announce" in the backfill section the answer cites. The answer instead argues "As far as I can see the bot is silent in the channel and only sends DMs. If so, most traders never see that GameX Companion exists." It also proposes building in-channel confirmations as the visibility fix. The visibility surface already exists and goes unused in the plan: a channel to promote in Moves 1 and 3, social proof via watcher counts, a ready demo for moderators. Tool log: "apps/bot/src (bot.ts, ingest-handler.ts, file list; grep for reply/send/DM)". `apps/api` was never opened.
3. **Misattributed quote:** "ADR 0005 keeps captures 'as OCR training data'." ADR 0005 contains no such phrase and does not mention training. It keeps the original image "so a better segmenter can be re-run over it later". The training label is in the bot code (`capture-client.ts:81` "Posts a training capture", `ingest-handler.ts:33` "Record a training capture"). The substance holds and the Discord AI-training check is a good catch, but the quote marks and the source are wrong.
4. **Misquoted file:** "Pre-build watches for the searches traders actually make (`lib/common-searches.ts` is a start, e.g. "40ias kb cruel")." The file holds four searches: "Eth War Fist, 400%+ ED, 40 IAS, self-repair", "Eth Fool's Feral Claws, 275%+ ED, self-repair", "Circlet, +2 Assassin skills, 20 FCR, 2 sockets", "Ring, 10 FCR, 100 AR, 30 life, 15 str". "40ias kb cruel" is VISION's example. The answer also leaves out that these searches are already "linked from the unfiltered search page", so part of the step is already done.
5. **Misapplied playbook citation:** "Paid ads, or launching on many servers at once. The playbook lists both under 'usually fails' at your stage." The playbook's "usually fails" cell for the first-community stage says "Launching on many **games** at once", and paid ads appear under the later "Spreading" stage. Changing "games" to "servers" changes the rule, and Move 3 itself pitches "3–5 more trade-server mods". It is smaller than round 1's 20–50 transplant, but the same kind of error: a playbook line reworded to support a point it doesn't make.
6. **Omission: season timing not worked out from the repo:** "I don't know the next season date. Check Blizzard's announcements." The repo has two data points: `knowledge/warlock-expansion.md` ("released Feb 20-21, 2026 alongside Ladder Season 13") and `research/plannersite-planner.md` (Season 14 live on 2026-09-21). Together they show the next season is probably months away, past the 90-day plan. They also show Season 14 is in its first weeks now (today is 2026-10-04), when trading is busiest. The answer neither places Move 3 on that calendar nor considers using the current season's early weeks, which is what INSTRUCTIONS #6 ("Consider timing against outside events") asks for.
7. **Evidence caveat dropped (repeat in kind):** "The Discord policy points come from Discord's own documentation, as cited in the playbook." The playbook's Sources line says "All read via search snippets." "[first-party, per the playbook]" is a partial hedge. The intents point is properly flagged ("Check the current Discord docs"), but the deletion and AI-training rules are passed on as documentation-backed with no snippet-only caveat.
8. **Tool use: economics step skipped silently; go/no-go numbers not modelled.** The `marketing_strategy` prompt step 4 says "run unit_economics or paid_media_math". The tool log says it was skipped and "I said so implicitly"; the answer itself never says so. No liquidity estimate was run (no such tool exists), so every stop condition stays qualitative. The `ab_test_sample_size` call was correct and reproduced exactly.
9. **Instruction breach: length.** About 1,466 words in the answer section against "keep the whole answer under about 1,200 words".
10. **Minor coverage gap:** the tool log lists "docs/adr/0001–0006". ADR 0007 (an owner's jewel assertion outranks a machine reparse, 2026-08-10) was not read. It doesn't change this plan, but it is part of the "shipped/partial" picture the answer claims to give.

## Server attribution (ranked, most impactful first)

1. **Inventory every distribution surface across the whole repo.** *Assistant caused (twice now); the server fix from round 1 was not applied.* INSTRUCTIONS #0 now asks for shipped/partial/planned status, but nothing tells the assistant to look for existing public outputs (feeds, webhooks, share links) or to search beyond the app it starts in. The public announce feed was missed again, and this time it reversed a conclusion ("most traders never see that GameX Companion exists").
   Fix (INSTRUCTIONS #0 in src/server.ts): "When a repo is attached, search the whole repo (every app and service, not one directory) for existing distribution surfaces: bots, webhooks, public channels or feeds, share links, public pages, sitemaps, emails. List them before proposing new ones, and check which are gated, flagged or admin-only."
2. **Require a code check of the mechanism the plan depends on.** *Assistant caused.* The answer took VISION's wording about sold items for the code's behaviour. Fix (INSTRUCTIONS #0): "When the core loop or core risk depends on how a feature behaves (when a notification fires, what triggers a match), open the code for that path and quote it. Treat vision and README text as intent, not behaviour."
3. **Add a liquidity / match-rate calculator.** *Server caused (still missing; round-1 fix #4 not applied); explains item 5 = 1 again.* `src/server.ts` registers no such tool. Fix as in round 1: `liquidity_estimate` (supply events/day, share matching a typical watch, window → expected matches per watch, P(zero matches), supply needed for a target fire rate). Reference it from `community-and-hobby-products.md` "Liquidity before reach" and from `marketing_strategy` step 4.
4. **Give free products a defined path through the economics step.** *Server caused (round-1 fix #3, second half, not applied).* `marketing_strategy` step 4 still reads "run unit_economics or paid_media_math with their numbers". Fix: "If there is no revenue model, say so in the answer, skip to the time and hosting budget, and state what would have to be true for money later."
5. **Give a length budget to each section, and make "cheapest test" and "cost" required fields.** *Server partly caused.* INSTRUCTIONS #6 lists "the mechanism, the cheapest test, the metric, a time box, and the stop condition", but the answer's moves have no "cheapest test" or "cost" fields, and the 1,200-word limit was missed by ~22%. Fix (src/prompts.ts `marketing_strategy` step 6): "Each move: one cheapest test (one action, not a build list), cost in hours or money, metric, time box, stop result that tests this move's own mechanism. Budget: summary ≤80 words, context ≤200, each move ≤150, 'not yet' ≤5 one-line bullets."
6. **Make the snippet-only caveat travel with each claim.** *Server caused (round-1 fix #7 partly applied).* `community-and-hobby-products.md` tags Discord rules inline as "[first-party]" but its only caveat is the footer "All read via search snippets." Fix: tag those lines `[first-party; snippet-only]` so excerpts carry the caveat, as `_conventions.md` should require.
7. **Work out event dates from the repo before saying "unknown".** *Assistant caused; the server can make it less likely.* Fix (`community-and-hobby-products.md` "Time launches to the game's calendar"): "Estimate the next event from known past dates in the user's material (e.g. previous season starts), state the estimate as an assumption, and say whether the current event's early weeks are still usable."
