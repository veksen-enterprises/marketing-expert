# Which page features, computable from HTML or a render, predict short dwell or bounce after an ad click? (checked 2026-10-27)

Question: ad platforms have built models that predict, from the landing page alone, whether people who click an ad leave fast. Which page features did those models use, how much did each matter, can a tool compute them the same way, and did any online test show that acting on them improved outcomes? This would change `audit_page` (`src/lib/pageAudit.ts`): whether to add fields or info flags such as text-to-link ratio, mobile readiness, click-to-call, form inputs or readability, and the wording of the existing viewport warning.

Access: the egress proxy refused curl for every host tried (archives.iw3c2.org, faculty.cc.gatech.edu, labs.yahoo.com, mounia-lalmas.blog, research.google, static.googleusercontent.com, gdac.uqam.ca, nyu.edu host, dl.acm.org, ir.webis.de), so every paper below was seen only through WebFetch, which returns a model's summary and chosen quotes. All marks are therefore `fetch summary`: figures are the tool's, unchecked against the text; re-check a figure before it enters a playbook. Searches with WebSearch.

Scope warning, for every finding below: these are **ads on Yahoo's mobile news stream (native ads) and Google or Yahoo sponsored search, 2008–2016**, thousands of advertisers, measured by the ad network. Dwell time is time until the user returns to the news stream or search page. These are not small product sites measured in their own analytics, and the pages were not changed by anyone.

Already in the repo, cited not repeated: Sculley et al.'s word-similarity result (correlation 0.180 vs 0.303) and expert-rating agreement, and Barbieri et al.'s noun-overlap ranking (`message-match.md` §2, §4); page speed and weight evidence (`page-speed-and-weight.md`); what readability formulas measure (`cro-landing-pages.md` §2); dwell-time curves on ordinary pages (`first-screen.md` §1); popups and interstitials (`overlays-and-carousels.md`).

## 1. What the models used, and which features carried weight

- **Lalmas et al. 2015 (Yahoo native ads, mobile).** 17 "content" features from the page: click-to-call, number of clickable elements, dropdowns, checkboxes, radio buttons and text inputs, media, viewport, window size (total width of div tags, to detect carousels), image height and width, number of images, a mobile-optimised flag, token count, noun scores, Wikipedia entity count, and a "summarizability" score. Plus 2 ad–page similarity features and 7 history features (past clicks, past dwell). [research, 1; fetch summary]
- Not in that paper: text-to-link ratio, load time, page size as such, popups, and readability (listed as future work). [research, 1; fetch summary]
- Importance (gradient-boosted trees, content features only): click-to-call 0.331, window size 0.125, number of clickable elements 0.113, radio inputs 0.089, dropdowns 0.084. With history added, past dwell time took 0.480 and 0.314 and the page features fell far behind. Ad–page noun similarity ranked 11th (0.023). [research, 1; fetch summary; ad level, ≥10 clicks per ad]
- Importance says how often a tree split on a feature, not which way it pushes. The paper gives no per-feature correlation or effect size. The one direction it states: form and input features had negative coefficients in the logistic model, read by the authors as hurting post-click experience. [research, 1; fetch summary; coefficients inside a multivariable model]
- **Barbieri et al. 2016 (same platform).** Added 11 "document object" features (link counts and ratios: internal, external, text size over link text size, main-text size over link text) and 8 readability features (Flesch–Kincaid on title, abstract and main text, token count, text sizes, summarizability). The text says "features extracted from the domain object and features related to the readability of the content are among the most important predictors." The importance values are only in a bar chart the fetch could not read; no numbers and no directions. [research, 2; fetch summary]
- **Sculley et al. 2009 (Google search ads).** Text only: terms parsed from keyword, ad and landing page, related terms, clusters, categories, and similarities. No links, images, page size, load time or popups; the authors name "link-based or other non-textual features" as future work. Landing-page terms alone gave correlation 0.198 with bounce rate, against 0.303 for all features; "terms from the creative text are more informative than those drawn from landing pages or keywords." [research, 3; fetch summary; offline]
- **Bron et al. 2017 (Yahoo search ads, mobile).** Target is an editor's 4-point mobile-friendliness grade, not behaviour. The 120+ features include HTML features (click-to-call, viewport tag, CSS file count, text length, HTML size, rendered width, word count, Gunning fog, clickable count, internal and external links), screenshot features (colour, texture, JPEG blockiness, symmetry) and 107 W3C mobileOK checks. [research, 4; fetch summary]
  - Weighted AUC for the editor grade: all features 0.788; mobile-optimisation features alone 0.752; window-size features alone 0.731; mobileOK alone 0.726; readability alone 0.589. [research, 4; fetch summary]
  - "The most discriminative feature is image width, i.e., the width of the rendered HTML image": pages wider than the phone were judged less friendly. [research, 4; fetch summary]
  - Editor friendliness correlated with dwell time at 0.26. [research, 4; fetch summary; "weak to moderate" in the authors' words per one fetch]
  - The two fetches disagree on conversions: one reports chi-square residuals (bad pages had more conversions than expected), the other says the paper gives no conversion statistics because the sample was too small. Not used. [derived]

Read together: a page-only model predicts long dwell modestly (Lalmas content-only logistic AUC 0.70; bounce AUC 0.61) and much better once the ad's own past behaviour is added (0.83–0.85). [research, 1; fetch summary] Most of the predictive power is in history, not in the page.

## 2. Single features alone: one observational result

- The only single page feature with a reported outcome difference is mobile-optimised vs not, in Lalmas et al. Over about 500 ads (about 65% optimised), moving from desktop to mobile, bounce rate fell 6.9% on average for optimised pages and rose 13.4% for the others (p = 0.003); dwell time fell for both, with no significant difference (p = 0.20). [research, 1; fetch summary; observational; the averages and medians point in different ways, medians −30.4% and −11.5%]
- "Mobile-optimised" there is not the viewport tag. It is a classifier trained on 259 hand-labelled ads from seven extracted features, including HTML size and apple-touch-icon. [research, 1; fetch summary] A tool checking only for a viewport tag measures something narrower.
- Readability alone predicted the editor grade poorly (AUC 0.589, where 0.5 is chance). [research, 4; fetch summary] No study here reports readability alone against bounce or dwell.
- Text-to-link ratio: only as a group inside a model (source 2), with no number or direction. A general search found SEO blog claims and no study. [derived; WebSearch]
- Load time, page size and popups: absent from all four models. Speed evidence lives in `page-speed-and-weight.md`.

## 3. Online tests changed which ads were shown, not the pages

- Lalmas et al.: a logistic model on page features ranked ads in Yahoo's iOS news app for about one month (May–June 2014; about 14,500 baseline ads and 12,500 ads in the test bucket; traffic share not stated). CTR +18% overall; median dwell +30% and average bounce −6.7% at ad level; user level +25% dwell and −12% bounce. [research, 1; fetch summary; one platform]
- Barbieri et al.: a survival random forest ranked ads on Yahoo mobile web for eight weeks. Dwell +13.3%, CTR +6.8%, bounce −10.3% (bounce = left within 5 seconds). [research, 2; fetch summary; traffic share not stated]
- Bron et al.: a model filtered out ads judged unfriendly; short clicks −6.04%, CTR +1.15%. Duration and traffic not reported. [research, 4; fetch summary]
- In every test the network showed fewer ads with bad pages. No test changed a page and measured the same page before and after. So these show the model can sort pages, not that fixing a feature (adding click-to-call, cutting links) lowers bounce on a given page. [derived]
- Lalmas et al. also found users whose ad clicks were short went on to click fewer ads than users whose clicks were long (ad-click change +90.3% vs +122.6%, p = 0.002; about 800 users per group). [research, 1; fetch summary; observational groups] That is the platform's reason to care, not a site owner's.
- One crowd experiment on 12 native-ad pages found video and advertorial style changed self-rated novelty and endurability, with no behavioural outcome. [research, 5; fetch summary; n=752 ratings] Too small and indirect to support a check.

## What this changes

1. **No new flags.** No feature here has a reported direction and size that a tool could apply on its own. The importances are tree-split shares inside a model, on ad-network pages, and the gain over chance came mostly from the ad's history. The online tests filtered ads; none changed a page. A flag like "low text-to-link ratio" or "no click-to-call" would claim a link the evidence does not show. [derived from 1–4]

2. **No new fields either, for now.** `audit_page` already returns the facts that overlap with these models: `wordCount`, `images`, `links` (internal and external), `forms` with field counts, and `viewport`. Adding a text-to-link ratio or click-to-call count as bare facts adds output the agent would read as meaningful, with nothing to say what a good value is. If a later lead finds a direction and size, revisit.

3. **Viewport warning: keep it, don't strengthen it.** Current text: "No viewport meta; page will render poorly on mobile." That is a rendering fact, true without any study, and it stays. Do not add a bounce claim to it: the one observational bounce result is for a broader "mobile-optimised" classifier on Yahoo ad pages, not the viewport tag. [research, 1; fetch summary]

4. **Optional, render mode only: "page wider than the phone screen."** Bron et al.'s top feature was the rendered page's width, and it is cheap to compute in render mode at a phone viewport: `document.documentElement.scrollWidth > window.innerWidth`. Input: render mode at a 390-px-wide viewport. Rule: scroll width more than a few pixels over viewport width. Output (info): "At a 390-px phone width the page is N px wide, so visitors must scroll sideways. Not checked: other phone sizes, content that loads after the render, and whether this changes how many visitors leave." Threshold: none beyond "wider than the screen", which is a rendering fact. Evidence: an editor-label association [research, 4; fetch summary; Yahoo ad pages], plus the plain fact that sideways scroll on a phone is a layout bug. This is a factual check, not a design grade, so it fits the owner's stance. Test: a fixed 1200-px-wide div gives one flag; a fluid page gives none.

5. **Playbook.** No tag changes. If `knowledge/landing-pages-and-cro.md` "Friction: … mobile layout" ever cites a source, the honest line is: "Ad networks rank down ads whose pages their models predict will be left quickly, and that raised dwell and clicks on the network [research; Yahoo, online tests of ad ranking]. No study here shows that changing one page feature lowers bounce."
