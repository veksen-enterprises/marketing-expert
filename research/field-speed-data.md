## 1. Who has real-user data

- **Rules.** An origin (a whole site, like `https://www.example.com`) or a page enters CrUX only if it is "publicly discoverable" and "sufficiently popular". Discoverable means the page returns HTTP 200 after redirects and is not marked `noindex` by header or meta tag; for an origin this applies to its root page. [first-party, 1]
- **The threshold is secret.** "An exact number is not disclosed, but it has been chosen to ensure that we have enough samples to be confident in the statistical distributions for included pages. The minimum number is the same for pages and origins." [first-party, 1]
- **Origin data is easier to get than page data.** An origin's count includes visits to all of its pages, against the same minimum. So a small site is more likely to have origin data than data for its home page. Splitting by device makes it harder still: the API guide warns that narrower queries include fewer visits and return "not found" more often, for less popular URLs and for tablets. [first-party, 1, 3]
- **Who is counted.** Only Chrome users on desktop and Android who share usage statistics and sync history without a passphrase. Chrome on iOS, Android WebViews and other Chromium browsers (Edge) are not counted. Google does not publish what share of users meet these rules. [first-party, 1]. A site whose visitors mostly use iPhones or Safari reaches the threshold later, and its data describes only its Chrome visitors.
- **Size of the dataset.** September 2026 release: 18,376,044 origins, and 55.9% of them have good Core Web Vitals. The count has stayed between about 16 and 18.5 million since 2022. [first-party, 4]. No first-party source gives the share of all websites this covers, and none was searched for.
- **Known gaps.** For some time, origins whose root page redirected (for example `/` to `/en/`) were left out of origin data; Google reported this fixed by early 2024. [first-party, 4]
- **Does a small product site have data? Not answered.** No source states the visitor threshold, and no small site was looked up (no API key). What the rules imply: a new or low-traffic site, or a site whose root page is `noindex` or redirects oddly, will often get "no data", and page-level data for a single landing page is rarer than origin data. [derived from 1, 3]. This is an inference, not a measured share.
- **Among sites that do have data, less popular is not slower.** Share of mobile sites with good Core Web Vitals by popularity rank, July 2025: top 1,000 51%, top 10,000 42%, top 100,000 37%, top 10 million 49%, all 48%. Desktop stays between 55% and 57%. [descriptive, 11]. So the tail of the dataset is not worse than the head; nothing is known about sites below the threshold.

## 2. What the two APIs need, return and send

- **CrUX API.** POST to `https://chromeuxreport.googleapis.com/v1/records:queryRecord?key=…` with a JSON body naming `origin` or `url`, optionally `formFactor` (`PHONE`, `TABLET`, `DESKTOP`) and `metrics`. A Google Cloud API key is required; an unkeyed call returns 403 "Method doesn't allow unregistered callers" (tested 2026-10-27). 150 queries a minute per project, free, and the quota cannot be raised. [first-party, 2; test]
- **What it returns.** For each metric, a three-bin histogram (share of visits good / needs improvement / poor) and a `p75` value, over a rolling 28-day window updated daily, with a `collectionPeriod` (first and last date). Metrics include `largest_contentful_paint`, `interaction_to_next_paint`, `cumulative_layout_shift`, `first_contentful_paint` and `experimental_time_to_first_byte`; the live page lists about 17 identifiers, some conditional. With no `formFactor`, values are pooled across devices and a `form_factors` share is returned. Google warns that percentiles are "synthetically derived" and do not mean any user saw that exact value. [first-party, 2]
- **URL handling.** The API strips fragments and some URL variations and reports this in `urlNormalizationDetails`; "complex actions like following redirects are not handled". It does not fall back from a URL to its origin; a caller must make a second query. [first-party, 2, 3]
- **No data.** The API answers 404 `NOT_FOUND`, "chrome ux report data not found". Google's guide gives three causes: the origin is not publicly navigable, the origin string is wrong (www or not, http or https: it must match the final URL after redirects), or "an insufficient number of samples". [first-party, 3]. So a 404 does not by itself mean "too little traffic".
- **History.** A separate CrUX History API gives the last 25 weekly 28-day windows by origin or URL. [first-party, 1]
- **PageSpeed Insights API.** Works "with or without an API key, although a key is recommended for frequent, automated queries". It runs a Lighthouse lab test on Google's servers and also returns CrUX data in `loadingExperience` (the page) and `originLoadingExperience` (the origin). But Google states: "We plan to discontinue including real-world data from the Chrome User Experience Report in this API. We recommend the CrUX API or the CrUX History API instead." No date is given. [first-party, 6]. Quotas were not stated on the pages read.
- **What each sends to Google.** CrUX API: the API key and the origin or URL string; Google learns that this key's project asked about that site. No page content is sent and Google fetches nothing. PageSpeed Insights API: the URL, after which Google's servers load and render the page. [first-party, 2, 6; derived]
- **Terms.** The Google APIs Terms of Service apply to both; they were not read. The doc pages are CC BY 4.0, which covers the docs, not the data. [first-party, 2, 5]

## 3. HTTP Archive byte fields are compressed (on-the-wire) sizes

- In HTTP Archive's crawl code, every byte summary (`bytesTotal`, `bytesHtml`, `bytesJS`, `bytesImg` and the rest) sums `respSize`, which is the HAR field `response.content.size`. [first-party code, 7]
- HTTP Archive's agent writes `content.size` as the same value as `bodySize`, taken from the request's `objectSize`. `objectSize` is the `Content-Length` header when the server sends one; otherwise the bytes Chrome received on the network (`encodedDataLength`); only if neither exists, the decoded size. A `Content-Length` on a compressed response is the compressed length. [first-party code, 7]
- So the figures are **compressed transfer sizes of the response bodies**, in most cases. Exceptions: a response with no `Content-Length` and a final network event can include header bytes, and a response with neither falls back to decoded size. The decoded size is kept separately (`objectSizeUncompressed`) but is not what the summaries add up. [first-party code, 7]
- This summary step has run in `HTTPArchive/wptagent` since at least November 2024 (issue #47 about `bytesHtmlDoc` points to that file). Code read today, not the exact build that ran in July 2025. The schema page does not say whether sizes are compressed. [first-party, 8, 9]
- **Effect on the proposed HTML flag.** The July 2025 home-page HTML figures (median 33 KB, 90th percentile 155 KB, mobile) are compressed sizes, and sum every HTML response on the page (iframes included) (`page-speed-and-weight.md` §5). HTML usually compresses to a fraction of its decoded size. A 1 MB decoded cut-off may therefore sit near the 90th percentile, not "well above" it as that note assumed. The ratio for a given page depends on its content; it was not measured here.

## 4. Heavy pages pass Core Web Vitals less often (correlation)

- **Web Almanac 2025.** HTTP Archive joined its July 2025 lab page weight (`bytesTotal`, compressed) to each page's own CrUX data, counting only pages with page-level LCP and CLS. A page "passes" if p75 LCP ≤ 2.5 s, CLS ≤ 0.1, and INP ≤ 200 ms or missing. [descriptive, 10; SQL read]

  | Home pages passing all Core Web Vitals | ≤1 MB | 1–2 MB | 2–3 MB | 3–4 MB | 4–5 MB | >5 MB |
  |---|---|---|---|---|---|---|
  | Mobile | 57% | 52% | 45% | 38% | 34% | 30% |
  | Desktop | 70% | 59% | 53% | 48% | 44% | 38% |

  Mobile home pages with good LCP: 72% at ≤1 MB down to 44% at >5 MB; median p75 LCP rises from 2.6 s to 3.8 s. CLS shows the same slope (88% to 71% good on mobile). Mobile INP barely moves (78% to 72%). Inner pages show a softer version of the same pattern (mobile: 68% to 42% passing). [descriptive, 10; figures from the chart descriptions]
- **Errors in that chapter.** Its text gives 63% desktop and 53% mobile for 2–3 MB home pages, where its chart description gives 53% and 45%. The inner-page LCP chart repeats the home-page values for 3 MB and up. Use the chart values above and round. [10, read]
- **Limits.** Cross-sectional: heavy pages come from different kinds of sites (media, shops with many images and ad scripts), so weight is not shown to cause the failures. The sample is pages popular enough to have page-level CrUX data; the chapter says it is "weighted toward more popular sites". It does not give the number of pages in each bucket. Weight comes from one lab load per page. [descriptive, 10, 11]. The HTTP Archive crawl list itself comes from CrUX origins, so all HTTP Archive reference numbers (including `page-speed-and-weight.md` §5) describe sites with enough Chrome traffic. [descriptive, 11]
- **Same direction elsewhere.** A 2026 practitioner analysis of 122,633 sites with phone field data: good LCP 89% under 1.2 MB, 85% at 1.2–2.5 MB, 79% at 2.5–5 MB, 74% over 5 MB. Its text and table disagree on bucket counts, and its data source is not named in the fetched text. [practitioner; 14]. In 2018, among the top 1,000 sites, fast-loading sites (CrUX onload) were far more common under 1 MB and slow ones over 3 MB, with exceptions both ways; charts only. [practitioner; 12]. In lab data alone, page weight correlated with onload at 0.20 and with first paint at 0.03 (about 4M sites, 2019). [practitioner; lab only; 13]
- **Request counts.** No analysis linking the number of requests to field pass rates was found. [search, 2026-10-27]
- **Size of the link.** Moving from the lightest to the heaviest bucket roughly halves the pass rate (57% to 30% on mobile home pages). Above 5 MB, about 7 in 10 mobile home pages with field data fail, against 4 in 10 under 1 MB. [derived from 10]. Weight alone does not decide the outcome: 30% of the heaviest pages still pass.

## What this changes

1. **Optional field-data lookup in `audit_page` (new outbound call: needs the security look in `CLAUDE.md`).**
   - Input: `MARKETING_EXPERT_CRUX_API_KEY` (an environment variable; off when unset) and the final URL after redirects from the audit's own fetch.
   - Calls: the CrUX API only, at the fixed host `chromeuxreport.googleapis.com` over HTTPS. Not the PageSpeed Insights API: Google plans to drop CrUX data from it, and it makes Google's servers load the page. Up to four queries: the URL and the origin, each for `PHONE` and `DESKTOP`.
   - Sends: the key and the origin or URL string. Nothing else. Skip the call (and say so) when the host is private or `MARKETING_EXPERT_ALLOW_PRIVATE=1` is set, so internal host names never leave. Never print the key, including in error text.
   - Output: per device, p75 LCP, INP and CLS with good / needs improvement / poor against the published thresholds, the `collectionPeriod`, and whether it is page or origin data. Label it "real Chrome users on desktop and Android over 28 days; iPhone and Safari visits are not counted".
   - On 404, write: "No real-user data from Google for this page/origin. Usual causes: too few eligible Chrome visits in 28 days, the root page is noindex or not HTTP 200, or the www/https form differs from the live one." Do not say "too little traffic" alone; it is one of three causes [3]. If page data is missing but origin data exists, say the numbers are for the whole site.
   - Without a key: one line, "Real-user speed not checked: set MARKETING_EXPERT_CRUX_API_KEY", never a silent skip.
   - Expect "no data" often for founder sites. That is inferred from the undisclosed threshold, not measured; see Open questions. Grade: [first-party docs].
2. **HTML byte flag (fetch mode): compare compressed with compressed.** HTTP Archive's 155 KB 90th percentile is a compressed size [7]. Compute a compressed size before comparing: use `Content-Length` when the response is compressed, or else gzip the decoded body locally (Node `zlib`, deterministic). Report both `htmlBytes` (decoded) and `htmlCompressedBytes` (with how it was found). Flag on the compressed size; the cut-off stays the project's choice. A cut-off of several times the 90th percentile (for example 500 KB compressed) keeps it a far-outlier flag. Wording: "…more than 9 in 10 home pages of sites in Chrome's dataset (HTTP Archive, July 2025)…". No study links HTML size alone to field results.
3. **Total-bytes flag (render mode): the wording may now cite field pass rates, not "likely slow".** Count transfer bytes (compressed, as on the wire), not decoded bytes, so the figure matches HTTP Archive's `bytesTotal`. Above 5 MB: "Among home pages that have Google real-user data, pages over 5 MB passed Core Web Vitals about half as often as pages under 1 MB (mobile 30% vs 57%; HTTP Archive Web Almanac, July 2025). That is a comparison across sites, not a measurement of this page; check real-user data (CrUX) before acting." Grade: [descriptive; cross-sectional; popular sites; one lab load per page]. Not "likely slow for real users": the link is correlational, 30% of the heaviest pages pass, and one render-mode load is not HTTP Archive's test setup. The 5 MB cut-off comes from the Almanac's top bucket; it is lower than the 11 MB 90th-percentile cut-off in `page-speed-and-weight.md`, so pick one and state where it comes from.
4. **Request-count flag: keep "comparison with other sites" only.** No field evidence links request count to pass rates. Keep the 90th-percentile wording from `page-speed-and-weight.md` §3 and do not mention real-user speed.
5. **Playbook `knowledge/landing-pages-and-cro.md`, Speed section.** Could add one tagged line: "Among popular sites, heavier home pages pass Google's real-user speed checks less often (mobile: 57% under 1 MB, 30% over 5 MB) [descriptive; cross-sectional; HTTP Archive 2025]". Also: "Google's real-user data needs enough Chrome traffic; a new site often has none, so use a lab test as a rough guide." Re-check the Almanac figures against the published chart before the first line enters a playbook.
